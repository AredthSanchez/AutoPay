# AutoPay file-by-file guide

This guide describes the current editable application at the repository root. Comments in source files explain non-obvious behavior and invariants. They do not change application logic. The historical ZIP is documented but intentionally preserved as a binary archive.

## How a request moves through the project

1. `index.html` loads `src/main.jsx`, which mounts `app/auth-shell.jsx`.
2. The shell obtains public login configuration from the Worker and uses Supabase for email/password identity. It supplies the current bearer token to `app/workspace/api.js`.
3. The selected business is sent with API requests. `worker/index.mjs` verifies identity through `worker/auth.mjs`; `lib/autopay/service.mjs` then checks D1 membership and required role before reading or changing business records.
4. The workspace renders invoices/clients and submits forms through the shared API transport. D1 stores business data; attachments use the optional bucket binding or the D1 chunk adapter.
5. Cron enters `worker/index.mjs`, then `lib/autopay/reports.mjs`, to queue due business reports and attempt email delivery. Cron does not use a browser session.

Supabase supplies identity, while Cloudflare D1 stores this application's business records. There is no direct browser access to those D1 tables. Account display metadata is not permission data.

## Important contracts

### Business scope and concurrency

The legacy `owner` column on invoices, clients, attachments, and notifications is a business ID, not an account ID. `X-AutoPay-Business` chooses a business but does not authorize access: `AutoPayService.scope()` verifies membership first. Owner-only actions call the role guard. Invoice writes include the version read earlier; concurrent edits return a conflict rather than silently overwriting a teammate's change.

### Invoice amounts, statuses, and dates

Prices are validated and summed in integer cents before conversion to displayed USD. Stored statuses are `OPEN`, `PAID`, and `VOID`; the UI derives `OVERDUE` from an open invoice's due date. Paid aging uses the recorded payment day. A paid status or manual payment entry is bookkeeping, not proof of bank settlement. The browser uses local calendar dates for its date helpers; assistant snapshots explicitly report UTC, and scheduled reports use their configured timezone.

### Banking and attachments

Bank ciphertext requires the original `BANK_DATA_KEY` and matching business/client context. A routing checksum validates syntax only. Keep keys out of Git and preserve them when migrating encrypted records. General client listings are separate from owner-only bank endpoints.

The service limits attachments to 5 MiB per file, 10 files and 25 MiB per invoice, and scopes metadata to the business/invoice. The D1 adapter chunks bytes into 128 KiB rows; R2 is optional. Uploaded content is downloaded as an attachment rather than treated as trusted application code.

### Chat and calls

The default `AUTOPAY_CHAT_MODE=testing` runs the deterministic local answer engine without contacting OpenAI. The optional `openai` mode requires a server secret and is subject to the service's usage/context limits. Both modes use a read-only sanitized snapshot. The paid path supplies at most 200 invoice/client detail records while totals cover all loaded records; the service rejects workspaces above its current 1,000-record limits.

Live collection calls are not implemented by the Cloudflare Worker. The call route rejects them; simulation records are explicitly marked as demo activity. This repository must not be described as collecting or transferring real money.

### Email delivery

New-invoice alerts and scheduled reports use persisted delivery records and Resend when configured. Scheduled reports contain current workspace totals, not just activity since the previous email. They exclude bank details, invoice notes, attachments, and client contact details. Provider acceptance is tracked as `SENT`; it is not proof the recipient read or received the message in their inbox.

Report scheduling scans UTC quarter-hours against the selected timezone and avoids a second run on the same local date during a daylight-saving fallback. Delivery leases reduce overlapping attempts; stable provider idempotency keys reduce duplicate sends. Failed/setup-pending runs remain visible for retry, subject to the existing attempt/time limits.

## Configuration reference

| Configuration                              | Meaning                                                                                                         |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------- |
| `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` | Public project identifiers used by the SDK and server verification. Never substitute a service-role/secret key. |
| `BANK_DATA_KEY`                            | Server-only base64-encoded 32-byte encryption key. Existing ciphertext requires its original key.               |
| `AUTOPAY_CHAT_MODE`                        | `testing` selects free local answers; only explicit `openai` enables the optional paid path.                    |
| `OPENAI_API_KEY`, `OPENAI_MODEL`           | Optional server-only provider credential and model override for paid chat. Not required for testing mode.       |
| `RESEND_API_KEY`, `MAIL_FROM_EMAIL`        | Server mail credential and sender for invoice alerts and reports.                                               |
| `RESEND_TEST_RECIPIENT`                    | Optional restriction matching the allowed test inbox until sender/domain setup supports other recipients.       |
| `DB`                                       | Worker D1 database binding for all business records.                                                            |
| `ASSETS`                                   | Built frontend static assets binding.                                                                           |
| `BUCKET`                                   | Optional object-storage binding; absent by default, so DatabaseFiles uses D1.                                   |

`package.json`, `package-lock.json`, and the deployment preflight's JSON-parsed configuration cannot contain ordinary comments. Their purpose is documented here instead. Do not commit real local secrets in example files.

| --------------------------- | ---------------------------------------------------------------------------------------------- |

| `npm run deploy`            | Builds, checks deployment config, and deploys to the configured Cloudflare account.            |

## Generated and ignored files

`node_modules/` is installed dependency code. `dist/` and `.worker-build/` are generated build outputs. `.wrangler/` contains local runtime state. `.dev.vars` and `.env*` may contain local credentials; only safe templates are tracked. SQLite files and `exports/` are local data, not source. Do not hand-document or edit each generated bundle: make changes in the source files listed above and regenerate them.

## Reading and maintenance order

Start with `README.md`, then this guide and `docs/PROJECT_GUIDE.md`. For a UI action, follow the component to `api.js`, the Worker authentication boundary, and the matching service route. For reports, follow settings to the outbox and cron processor. Tests provide executable examples of the important business/security contracts.

Add future schema changes as new migrations rather than rewriting executed SQL. Update this index whenever tracked files are added or removed. Keep comments focused on constraints, data flow, and reasons; avoid narrating every JSX element or assignment.
